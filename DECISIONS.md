# DECISIONS.md — Call Analysis product decisions

Workspace-level decisions (D-01…D-18) live in the parent `DECISIONS.md`. This file records the
choices made inside this product. Format: `D-CA-nn · date · decision · why · consequences`.

| # | Date | Decision | Why | Consequences |
|---|---|---|---|---|
| D-CA-01 | 2026-09-12 | **Next.js App Router owns routing; the platform `App` router is not mounted.** `lib/api.ts` is a thin adapter that gives every `app/api/v1/**/route.ts` handler the platform's pipeline: request id, auth, per-IP token bucket, OpenAPI validation, problem+json, security headers, access log and usage counters. Session cookies are signed by a real platform `App` instance so the HMAC format matches every other ARAG product; `authenticate` and the rate limiter are ported (≈60 lines) because they need `IncomingMessage`. | Two routers in one process cannot both own `/api/v1`, and Next's file-based routing is the reason the framework was kept (D-04). | One small adapter to keep in step with the platform; `test/unit/api-adapter.test.ts` pins the ported logic, and the contract tests assert spec/implementation parity in both directions. |
| D-CA-02 | 2026-09-12 | **Route coverage is asserted from `API_ROUTES` plus a filesystem walk of `app/api/v1`,** not from `missingFromSpec(app, doc)`. | That helper needs a platform `App` instance, which this product does not build. | `test/contract/openapi.test.ts` fails if a handler is added without a spec entry, if a spec entry has no handler, or if `API_ROUTES` drifts from either. |
| D-CA-03 | 2026-09-12 | **`ARAG_BASE` is renamed `ARAG_BASE_URL`, with the old name read as a fallback.** | The platform standardises on `ARAG_BASE_URL`; the deployed Fly app and existing `.env.local` files still set `ARAG_BASE`. | `applyLegacyEnvAliases()` maps it at boot; documented in `.env.example` and covered by a test. The alias can be dropped once the Fly secret is renamed. |
| D-CA-04 | 2026-09-12 | **Reads are cached in-process (catalog ids, per-call summaries and details, labelsets, dashboard) with a 60 s TTL, single-flight loading and explicit invalidation on upload/delete/provision.** | The audit measured ~600 ARAG requests per dashboard view at 200 calls; rails multiplied it. A TTL cache with de-duplicated loads collapses that to one fetch per call per window. | Freshly uploaded calls can be up to `CALLS_CACHE_TTL_MS` stale in aggregates; uploads and deletes invalidate immediately, and the admin panel can clear the cache. Multi-machine deployments cache per machine — documented in `docs/architecture/scaling.md`. |
| D-CA-05 | 2026-09-12 | **`POST /api/v1/calls` creates the resource synchronously and returns `202` with a job that waits for transcription.** | The caller needs the call id and a `Location` immediately; only transcription and retrievability are slow. Keeping the recording bytes out of the persisted job input also keeps `DATA_DIR` small. | The job's input is `{callId, title, transcribed}`; the upload itself is bounded by `MAX_BODY_BYTES` and a MIME allowlist. |
| D-CA-06 | 2026-09-12 | **The taxonomy (`lib/domain/taxonomy.ts`) and the 24 demo scenarios (`lib/domain/scenarios.ts`) moved out of `scripts/` into the product,** and the scripts became thin HTTP clients of `/api/v1`. | The labelsets and agents are product behaviour — the admin panel provisions them and the mock seeds from them. Scripts that reimplement ingestion drift from the API. | `scripts/*.ts` need a running server and hold no ARAG credentials of their own; `scripts/reset.ts` additionally refuses a live Knowledge Box without `CALLS_ALLOW_DESTRUCTIVE=1`. |
| D-CA-07 | 2026-09-12 | **macOS `say` + `ffmpeg` media rendering is optional.** `scripts/gen-media.ts` writes a transcript-only manifest when they are unavailable. | The product must be buildable and demoable on Linux and in CI; rendered audio is a nicety for the live demo only. | Documented in `docs/developer/local-dev.md`; the mock ARAG synthesises timestamped transcripts either way. |
| D-CA-08 | 2026-09-12 | **`ARAG_MOCK=1` seeds the mock Knowledge Box with real transcripts and then runs the product's own labeler and ask agents against it at boot.** | A demo mode that shows empty charts is not a demo. Running the real taxonomy against the mock proves the agent definitions as well as the UI. | First request after boot pays the seeding cost (~1 s for 13 calls); `CALLS_MOCK_SEED` tunes the corpus size. |
| D-CA-09 | 2026-09-12 | **The REMi answer-quality call stays best-effort and time-capped, and is skipped entirely for a declined answer.** | `/predict/remi` can fail or be slow, and it scores topical relevance rather than whether an answer was given — it rated a refusal as high confidence in the live 3 Sep audit. | The badge falls back to the citation-coverage floor; a decline shows no badge at all. |
| D-CA-10 | 2026-09-12 | **Generated metric values are validated against the taxonomy enums before they reach a chart** (`sanitizeMetrics`). | A model can return prose where an enum was requested; "Not enough data to answer this." once rendered as a line-of-business category. | Invalid values are dropped, not displayed; the dashboard reports `withMetrics` so the gap is visible. |
| D-CA-11 | 2026-09-12 | **`lib/version.ts` holds the product version instead of importing `package.json`.** | The OpenAPI module is imported by Node-run CLI scripts, which have no bundler to resolve a JSON import (and Node requires an import attribute). | A contract test asserts the constant matches `package.json`. |
| D-CA-12 | 2026-09-12 | **`bun audit` is a real CI gate via `scripts/audit.ts`, with an explicit, dated allowlist in `.audit-allowlist.json`,** instead of `bun audit \|\| true`. | The corporate registry blocks releases newer than ~14 days, and TEAM-BRIEF pins `nanoid` and `baseline-browser-mapping` to older versions for exactly that reason, so a bare `bun audit` can never pass. Masking it with `\|\| true` would also hide a genuinely dangerous finding. | `make audit` and CI fail on any un-waived advisory at or above `high`. Every waiver names the package, why it is not reachable from a request path, and a review date (2026-12-01). |
| D-CA-13 | 2026-09-12 | **Creating and deleting calls uses a dedicated `write` auth mode: the admin token or an API key, never the freely issued demo session cookie.** A deployment with no credentials configured at all may still write (local mock demo), but never in production. | The platform's `api` mode is open when `API_KEYS` is unset, which is the shipped default — an independent review demonstrated an unauthenticated `DELETE` removing a call from the Knowledge Box. Reads staying open keeps the demo one command; destruction must not. | `POST /api/v1/calls` and `DELETE /api/v1/calls/{id}` are `auth: "write"`; `NODE_ENV=production` with neither `ADMIN_TOKEN` nor `API_KEYS` refuses writes with an explanatory 403. Covered by integration tests in all three configurations. |
| D-CA-14 | 2026-09-12 | **CORS is implemented in the adapter and every `/api/v1` route module exports the shared `preflight` handler as `OPTIONS`.** | `ALLOWED_ORIGINS` was read into the environment, shown in the admin config view and documented in `.env.example`, but nothing consulted it — an operator would have believed cross-origin access was restricted when no CORS header was emitted at all. | Same-origin stays the default (empty `ALLOWED_ORIGINS` emits no CORS headers, exactly as before); an allowlisted origin now gets correct headers and working preflight. The contract tests ignore `OPTIONS`, since it is a CORS mechanism rather than an API operation. |
| D-CA-15 | 2026-09-12 | **Per-route rate limits are expressed as a multiplier of the deployment's configured bucket, not as absolute values** (`rateLimitMultiplier`: 20 for media, 0.25 for ask), even though the platform's `App` offers absolute `rateLimit: { rps, burst }` per route. | A limit that stays proportional to `RATE_LIMIT_RPS` means raising the deployment's limit does not silently leave the media route pinned to a hard-coded value, and tests, the showcase and local development need no special cases. Media needs a *looser* bucket (a scrubbing player bursts Range requests); ask needs a *tighter* one (retrieval + generation + REMi is the most expensive call in the API). | Each of those routes gets its own bucket keyed by method, path and client, so neither drains nor is drained by the shared one. |
| D-CA-16 | 2026-09-12 | **Every test, Playwright and build command starts with `ENV_FILE=/dev/null` AND explicitly blanked `ARAG_KB_ID`/`ARAG_API_KEY`/`ARAG_BASE_URL`/`ARAG_BASE`; Playwright uses a fixed product-specific port (3241).** | A developer `.env` in this repo holds live Knowledge Box credentials. `ENV_FILE=/dev/null` alone is **not** enough in a Next.js app: Next loads `.env`/`.env.local` itself before any product code runs, and only skips keys already defined — verified live, a server started with `ENV_FILE=/dev/null` and no `ARAG_MOCK` still connected to the real Knowledge Box. Blanking the keys makes them "already defined" so Next leaves them alone. A sibling product's Playwright on the shared default port also produced one spurious showcase failure. | `make e2e`, `make showcase` and the integration harness are hermetic (an integration test asserts the effective KB id is the mock one); `PW_PORT` still overrides. |
| D-CA-17 | 2026-09-12 | **`make test`/`make coverage` build first, and the integration harness also rebuilds when a source file is newer than `.next/BUILD_ID`.** | The harness drives a real `next start`, so a stale build made the suite test code that was no longer there — a source fix appeared to fail, and a source break would have appeared to pass. | Deterministic runs at the cost of a few seconds; `bunx vitest run` on its own is still safe thanks to the staleness check. |
| D-CA-18 | 2026-09-12 | **White-label branding is configuration, not a fork**: `BRAND_*` variables parsed by the platform's `readBranding(env, defaults)` (arag-platform 0.1.6), served at the public `GET /api/v1/branding`, read server-side by the root layout, `AppChrome` and the admin layout, and shown in the admin Config page. | Workspace D-25/D-26: the audience is Progress and its ISV partner network, and a partner must be able to ship this under their own identity without maintaining a fork. Using the platform parser keeps the keys and precedence identical across all three products. | `lib/branding.ts` is the only module that reads a `BRAND_*` key. Colours reach the UI as CSS custom properties that override the UI-kit tokens the Tailwind theme maps to, so one variable re-colours the demo and the admin console together. |
| D-CA-19 | 2026-09-12 | **Branding values are re-validated in this product before they are rendered**, on top of the platform parser: colours against a strict hex/`rgb()`/`hsl()` grammar, logo and support URLs against an http(s)/same-origin allowlist, free text bounded to 200 characters. | The platform applies colours with `element.style.setProperty()`, where its looser `rgb(.*)` grammar is harmless. This app is server-rendered and interpolates the colour into a `<style>` element, where the same value could close the declaration and inject a rule. Reported upstream. | An invalid value falls back to the product default rather than breaking or injecting. Covered by unit tests, including the injection strings. |
| D-CA-20 | 2026-09-12 | **An explicitly empty `BRAND_TAGLINE` or `BRAND_FOOTER_TEXT` means "show nothing", not "use the default"** — a deliberate one-line divergence from the platform parser. | A partner must be able to remove the tagline and the demo-data footer line entirely; the platform treats an empty variable as unset. | Documented in `docs/developer/white-label.md` and pinned by a unit test. Every other key follows platform semantics exactly. |
| D-CA-21 | 2026-09-12 | **The product experience is an application shell — a Progress band, a persistent left sidebar (Dashboard, Calls, Upload, Agents & Taxonomy, Settings, Admin), a page header and a content area — and the admin panel lives inside it rather than beside it.** The bespoke five-bar waveform wordmark in `AppChrome.tsx` is deleted; the file is gone. | Workspace D-28: the owner rejected a set of pages framed as a "studio". An operator is not a different species of user with a different design language, so one shell serves both, and a partner white-labelling this gets one consistent product rather than two. | `components/shell/AppShell.tsx` owns identity, navigation and the live deployment strip for every route. Adding a screen without adding it to the nav is now visible. Old admin paths (`/admin/health`, `/admin/config`, `/admin/agents`, `/admin/cache`) redirect, so existing links and docs keep working. |
| D-CA-22 | 2026-09-12 | **The default product identity is the official Progress Agentic RAG wordmark SVG** (`public/brand/arag-logo.svg` on light surfaces, `arag-logo-alt.svg` on ink), never recoloured; Progress green `#5ce500` is a fill-and-dark-surface colour only, declared as `--pg-green` and never reassigned onto a kit token. `BRAND_POWERED_BY=0` removes the band, the footer credit **and** the wordmark together. | `#5ce500` measures 1.66:1 on white — it fails every contrast threshold as text or as a hairline on a light surface — but 11.1:1 on `--arag-ink-950`. Confining it to Progress-owned surfaces makes the white-label rule fall out for free: the surfaces that carry green are exactly the surfaces the credit toggle removes. | Interactive colour stays `--arag-brand-600`; positive semantics stay `--arag-accent-500`/`--arag-accent-fg`. A white-labelled deployment with no logo of its own shows its product name set in type rather than a Progress mark it is not entitled to — asserted by `test/e2e/branding.spec.ts`. |
| D-CA-23 | 2026-09-12 | **`public/ui-ext.css` holds the new components, authored in UI-kit style** (`.arag-*` class names, `--arag-*` tokens, no Tailwind, no product-specific selectors) so the Head can lift the file into `arag-platform/ui/arag-ui.css` unchanged. | The kit had no application shell, data table, drawer, filter bar, stat strip, pagination, menu, segmented control, skeleton or media track — every ARAG product will need all of them, and building them as Tailwind soup inside this repo would make them unliftable. | The file is imported by `app/globals.css` and also served at `/ui-ext.css`. It ends with a clearly-marked compatibility block working around three kit bugs (see the platform-gaps section of the final report); those rules are the only part that should not be lifted verbatim. |
| D-CA-24 | 2026-09-12 | **`GET /api/v1/calls` returns the facet tallies, agent list and queue list alongside the page**, with facets counted over the structurally-filtered set but *before* the label filter is applied. | A filter bar that shows live counts needs them computed server-side, and one request beats four. Counting facets after the label filter would collapse every other facet to zero as soon as one was selected, which makes a facet list unusable. | `CallPage` gains `facets`, `agents` and `queues`. The table is one `GET /api/v1/calls` per view. Documented on the operation and covered by a contract test. |
| D-CA-25 | 2026-09-12 | **Every call carries a derived `lifecycle` — queued, transcribing, labelling, partly analysed, analysed, failed — computed in `lib/lifecycle.ts` from the Knowledge Box processing status, the labels applied and the generated fields present.** It is never stored. | ARAG reports three signals that arrive independently and at different times; a reviewer scanning a list needs one word and a "what do I do next". Storing it would let a Knowledge Box that was emptied or re-provisioned outside the product report a state that is no longer true. | The chip appears in the table, the workspace header and the ingest history, and is filterable (`?lifecycle=`). `LIFECYCLE_COPY` carries the one-sentence explanation shown on hover, so colour is never the only signal. |
| D-CA-26 | 2026-09-12 | **"Re-run analysis" refreshes one call rather than re-invoking a model for it**, and says so. The job clears every cached derivative, waits for the Knowledge Box to report the resource processed, re-reads it, and reports whether an analysis is actually present afterwards. | ARAG's data-augmentation agents are Knowledge-Box-wide tasks, not per-resource invocations. Claiming a per-call re-run would be a lie the product could not honour; refusing to offer the action at all would leave a reviewer with no way to pick up a taxonomy change. | The operation description and the UI both name the limitation and point at Agents & Taxonomy → Re-provision for a genuine agent re-run. The path stays American (`/reanalyze`, `reanalyzeCall`) to match the existing `call_analysis` field vocabulary; the UI copy is British ("Re-run analysis"). |
| D-CA-27 | 2026-09-12 | **Share links are `api`-level auth, not `write`,** and are the one deliberate exception to D-CA-13. A link is a random 256-bit token, expiring (7 days by default, 90 maximum) and revocable; an unknown, revoked and expired token are all an identical 404. | A share link writes application state, never the Knowledge Box, and grants no access the open read API does not already give — requiring a credential to create one would simply mean nobody could. What matters is that every link has a visible creation time, an expiry and a revoke button, which is what turns "send this to the supervisor" into an auditable action. | `POST/GET /api/v1/calls/{id}/shares` and `DELETE /api/v1/shares/{token}` need whatever a read needs on the deployment; `GET /api/v1/shares/{token}` is public because the token *is* the credential. A contract test pins the exception and asserts the spec explains it, so it cannot be widened by accident. |
| D-CA-28 | 2026-09-12 | **First-run onboarding is computed live on every read, never stored**, and the guided demo is the same four-step screen with a real seeding job behind it — there is no demo-only route and no scripted overlay. | A stored checklist goes stale the moment a Knowledge Box is emptied, re-provisioned by script, or connected somewhere else, and a demo that runs on a separate code path stops being evidence of anything. | `GET /api/v1/onboarding` derives the four steps from the catalog, the taxonomy and the agent state; `POST /api/v1/samples` runs a repeatable job that provisions first, then uploads the shipped scenarios, skipping slugs that are already present. The showcase recording simply follows a person using it. |
| D-CA-29 | 2026-09-12 | **Exports are `GET` with the filter in the query string, not `POST` with a filter body** (the design spec proposed the latter). | A `GET` is an ordinary download link: `<a download href=…>` works, the browser owns the save dialogue, and the URL is the proof that what was exported is exactly what was on screen. A `POST` would need a fetch, a blob and a synthetic anchor to achieve the same thing, and could not be copied into a terminal or a scheduler. | `GET /api/v1/calls/export` shares `CALL_FILTER_PARAMS` with the list route, so the two can never disagree about what a filter means; an explicit `ids` selection overrides the filter. CSV cells beginning `=`, `+`, `-` or `@` are prefixed with a quote so a transcript line cannot execute as a spreadsheet formula. |
| D-CA-30 | 2026-09-12 | **Scope deliberately cut from the design spec, recorded rather than silently dropped:** in-product labelset editing (`PUT/DELETE /api/v1/labelsets/{id}`), in-product API-key management, job cancellation, dashboard date-range scoping, saved views, and the column picker / density toggle. | All are P1/P2 in the spec's own priority list, and none is load-bearing for "would a customer recognise this as a product". The taxonomy screen is read-only but shows everything an operator needs to diagnose a labelling problem; API keys are an honest placeholder that says where keys come from and that in-product management does not exist yet. | Listed as known gaps in the final report with the exact endpoints already specified in `design/PRODUCT-EXPERIENCE.md` §2.3, so the next pass has no design work to redo. |
| D-CA-31 | 2026-09-12 | **`lifecycle: "analysed"` requires the written narrative, not just the flat metrics**, and a summary read (which never fetches the narrative) is distinguished from a detail read that looked and found none — `analysis: undefined` means "not looked for", `analysis: null` means "absent". | The first implementation accepted an `analysis` argument and never read it, so a call whose metrics agent finished before its ask agent reported itself fully analysed, hid the Re-run affordance and sat in the analysed count. Found by the independent QA review. Requiring the narrative unconditionally would have been the opposite error: every row in the table would read "partly analysed", contradicting the detail page. | `test/unit/lifecycle.test.ts` is exhaustive over the inputs — the state was shipped with no unit tests at all, which is precisely how the bug got through. |
| D-CA-32 | 2026-09-12 | **The call list looks up each call's own ingest job and folds its status into the derived lifecycle**, after the cache rather than inside it. | Without it, `queued` and job-level `failed` were states the product defined, documented and offered as a filter but could never display: ARAG reports a freshly created resource as PENDING ("transcribing") and says nothing about a call that has been accepted but not picked up. Jobs are in-memory and keyed by `ref`, so this is a map lookup, not a round trip. | Applying it after the cache means a cached summary cannot freeze a job state that has since moved on. |
| D-CA-33 | 2026-09-12 | **An action the deployment will refuse is not rendered.** The calls table, the workspace kebab and the bulk bar take `canWrite` from `GET /api/v1/settings` (server-side), and the product's Agents & Taxonomy screen links to `/admin/taxonomy` instead of offering a Re-provision button that would answer 401. | The design spec's rule is that an offered action is never allowed to fail. Discovering you are not permitted *after* clicking Delete is the worst moment to find out, and on a read-only deployment the affordance is simply noise. | Export stays available everywhere, because it needs only a read. The bulk bar shows "Read-only" with the reason on hover rather than disabled buttons with no explanation. |
| D-CA-34 | 2026-09-13 | **Environment variables become defaults and the settings store becomes the authority.** Every value the product reads from configuration — branding, connection, limits, retention — is editable at `PUT /api/v1/settings/{section}`, persisted in `DATA_DIR/settings.json`, and applied by mutating the memoised runtime container in place (`rt.env`, `rt.branding`, and a wholesale replacement of `rt.arag`). `DELETE` restores the environment default from a snapshot taken at boot. | The owner's bar is that nothing configurable is read-only in the UI, and that a change takes effect without a restart. The alternative — an `effectiveSettings()` object every consumer must remember to consult — is one forgotten call site away from a setting that saves and silently does nothing. Mutating the container means every existing read path picks the new value up for free. | `rt.envBranding` and `rt.envDefaults` exist solely so a reset is a real operation rather than a redeploy. A cache-TTL change swaps `rt.cache` (its `ttlMs` is readonly by design), discarding entries admitted under the old policy. Connection edits are ignored in mock mode: re-pointing the in-process sample Knowledge Box would break the sample data with no way back through the UI. |
| D-CA-35 | 2026-09-13 | **Secrets are write-only, never write-then-read.** `connection.apiKey` is accepted by the settings write and never returned by any read model; the UI shows "set · rotate". An empty string means "leave it alone", not "clear it". | A settings screen that round-trips a credential is a second place to leak it, and a form that posts back what it rendered would clear the service-account token the first time an operator saved an unrelated field. Clearing it from a form would also take the deployment offline with no route back through the product. | An integration test asserts `GET /api/v1/settings` never contains an `apiKey` key; the audit trail reduces the value to `true`. |
| D-CA-36 | 2026-09-13 | **API keys are stored as SHA-256 digests in a real key store, and `API_KEYS` becomes a one-time seed rather than the mechanism.** Creation returns the material exactly once; `lastUsedISO` is written at most once a minute per key; revocation never deletes the row. | The placeholder told the truth ("keys come from the environment") but made key management impossible without a redeploy. Hashing means a leaked `apikeys.json` grants nothing. SHA-256 rather than a password KDF is deliberate: the token is 192 bits of `randomBytes`, so there is nothing to brute-force offline and a slow hash would only make every authenticated request slower. Throttling last-used stops a read-only API call from becoming a disk write. | Seeding is idempotent by digest, so restarting never duplicates a row and re-adding a removed variable resurrects the same row — still revoked if it was revoked. Revoking rather than deleting keeps the "what did this key touch, and when" evidence an incident review needs. Verification compares every active key even after a match, so timing reveals neither which key matched nor how many exist. |
| D-CA-37 | 2026-09-13 | **The taxonomy moves out of the source tree into an editable store.** `lib/domain/taxonomy.ts` seeds `DATA_DIR/taxonomy.json` on first read; labelsets are then created, edited and deleted in the product, and the labeler agents' `operations` are *derived* from the current labelsets on every read rather than stored. | The shipped health-insurance vocabulary is a default, not a constraint — a partner classifying utility calls needs different reasons and outcomes, and asking them to fork the repo for that is the difference between a product and a sample. Deriving the agent operations is what stops a labelset edit and the agent that applies it from drifting apart. | A labelset id is immutable after creation (the path id wins over a body id) because renaming it would orphan every label already applied upstream. Deleting removes it from the product's vocabulary; `?knowledge_box=true` additionally deletes it upstream, which destroys labels already applied to analysed calls — data, not configuration, so never the default. |
| D-CA-38 | 2026-09-13 | **Retention has no background sweeper.** The policy (`days`, `enabled`) is recorded and previewable at any time, and deletion happens only when a person or a scheduler calls `POST /api/v1/retention/purge`. `days: 0` means "no limit", not "delete everything". | A timer removing a partner's call recordings unattended on a Sunday night is the failure mode worth engineering away, and it is what a default-valued field read destructively would produce. A preview that shares one code path with the purge cannot disagree with it about scope. | Purging is admin-only and irreversible; share links pointing at a purged call are revoked in the same pass so no live URL resolves to nothing. A single run is capped at 200 calls. |
| D-CA-39 | 2026-09-13 | **Saved views are stored on the server and shared, not in each browser; column choice and row density are stored per browser and are not.** | A view is a named definition of a queue — a rota of supervisors reviewing the same work should see the same definition, and one person's `localStorage` cannot deliver that. Column and density are furniture: a link someone sends should carry the question, not the recipient's preferences. The stored query is re-parsed through an allowlist on write, because a saved view is a URL the product will follow. | Saved views sit at read-level auth alongside share links (D-CA-27): they write application state only and grant no access the read API does not already give. The contract test's mutation rule exempts both, by name and with the reason. |
| D-CA-40 | 2026-09-13 | **Hot read models are served stale-while-revalidating.** `catalogIds` and `summaryOf` return an expired entry immediately and refresh behind it for up to nine further TTLs; the dashboard aggregate is no longer cached under a key of its own. | This is the fix for the eight-second calls-list stall seen after a dashboard drill-through in the re-recorded showcase. `dashboard:all` was written only when its loader resolved, so it was stamped later than the `summary:<id>` entries it was built from; for that difference the dashboard rendered instantly from its own entry while re-warming nothing, and the next screen to read — the calls list, one click later — paid the whole 1 + N fan-out. Raising the TTL would only have widened the stale window without removing the cliff. | `aggregate()` is pure and O(N) over a few hundred rows, so re-running it per render costs nothing measurable and every dashboard render now re-warms exactly what the calls list reads next. Staleness stays bounded by the TTL because every mutation invalidates the key outright rather than letting it age out. `/calls` also gets its own `loading.tsx`, and the dashboard's ~35 drill-through links drop Next's prefetch, which was saturating the browser's connection pool immediately before the click. |
| D-CA-41 | 2026-09-13 | **The API explorer renders `/api/v1/openapi.json` at runtime rather than a hand-maintained operation list,** and lives at the `/api` page route alongside the `/api/v1/*` handlers. | The bar is that every API capability is exercisable in the UI; a hand-written list satisfies it on the day it is written and not afterwards. Reading the served document means an operation added to the spec tomorrow appears with no code change — which is also what makes the coverage claim checkable rather than asserted. | A unit test walks every operation in the real document through the explorer's indexing and form generation, so the coverage guarantee is a test rather than a promise. Destructive operations need a second click: this is a live API against the deployment's real Knowledge Box. |
| D-CA-42 | 2026-09-13 | **Settings, API keys and retention writes are operator-only (`auth: "admin"`); taxonomy and saved-view writes are not.** | An API key is a credential for using the product's data. It must not be able to re-point the deployment at a different Knowledge Box, mint itself a new key, or purge the corpus — those change the deployment for everyone, which is the operator's job. Editing a labelset changes what the product classifies with, which is the product's job. | Server components use `lib/session.ts` (`isOperator()`) to render editable controls or an honest read-only view with a route to sign in, rather than a form that 401s on Save; the route still checks.
