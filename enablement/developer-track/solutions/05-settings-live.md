# Solution — Exercise 5: change a setting live

Executed against the sample deployment while this was written.

## The sequence

```
1. POST /api/v1/calls/{id}/ask   (110-char question)          → 200
2. PUT  /api/v1/settings/limits  {"maxQuestionChars": 60}     → 200
     limits: {maxQuestionChars: 60, maxUploadBytes: 104857600,
              rateLimitRps: 5, rateLimitBurst: 20, cacheTtlMs: 60000}
     overridden: ["limits"]
3. GET  /api/v1/settings         (no credentials)             → maxQuestionChars 60
4. POST /api/v1/calls/{id}/ask   (the identical request)      → 400
     {"type":"https://arag.dev/problems/bad-request","title":"Bad request","status":400,
      "detail":"question must be at most 60 characters",
      "instance":"/api/v1/calls/demo…0013/ask","requestId":"f911fdcc-…"}
5. GET  /api/v1/admin/audit                                   → settings.limits by operator,
                                                                 detail {"maxQuestionChars": 60}
6. DELETE /api/v1/settings/limits                             → maxQuestionChars 500, overridden []
7. POST /api/v1/calls/{id}/ask   (same request again)         → 200
     GET /api/v1/admin/audit?action=settings.limits.reset     → one entry, actor operator
```

No restart. `GET /api/v1/admin/health`'s `uptimeSec` climbed monotonically across the whole
sequence.

Step 4 is the proof, and the detail string is the part worth pointing at: the error names **60**.
It was generated by reading the value you wrote a moment earlier out of the live runtime, not by a
constant compiled at boot and not by a schema regenerated on restart.

## Step 7 — the authorisation boundary

```
PUT /api/v1/settings/limits   with X-API-Key  → 401
  {"title":"Unauthorized","status":401,"detail":"Admin token required", …}
POST /api/v1/views            with X-API-Key  → 201
```

One key, two endpoints, two answers. That is `DECISIONS.md` **D-CA-42** in a pair of requests.

## How "no restart" is actually true

`applyToRuntime()` in `services/config.ts` runs twice in a deployment's life *per change*: once at
boot (from `buildRuntime()`) and again at the end of every `updateSettings()` / `resetSettings()`.
It does not build a new runtime — it **mutates the memoised one on `globalThis` in place**:

- `rt.branding` is replaced with a merged object, re-validated through `safeColor`/`safeLogoUrl`.
- `rt.env.maxQuestionChars`, `maxUploadBytes`, `rateLimitRps`, `rateLimitBurst` are assigned.
- If `cacheTtlMs` moved, `rt.cache = new TtlCache(newTtl)` — a whole new cache.
- In **live** mode, if any connection field moved, a new `AragClient` is constructed and assigned
  to `rt.arag`, and `rt.cache.clear()` runs because every cached entry came from the previous
  Knowledge Box. In **mock** mode the whole connection branch returns early.

The alternative design — an `effectiveSettings()` object every consumer must remember to consult —
is one forgotten call site away from a setting that saves, displays as saved, and silently does
nothing. Mutating one container means a call site cannot forget, because there is nothing to
remember: it reads `rt.env.maxQuestionChars` the way it always did.

## Answers

**1. Why `admin` and not `write`?**

An API key is a credential for *using* the deployment's data — upload a call, read one, share one.
Changing settings means re-pointing the deployment at a different Knowledge Box, rotating its
service-account credential, raising its own rate limits, or turning off the retention policy. A key
that could do that would be a key that could escalate itself, and a customer who issued keys to
three integration partners would have issued three ways to take the deployment offline. So
settings, API keys and retention are operator-only (`auth: "admin"`), while taxonomy and saved views
— which change what the product *classifies* and what a team *looks at* — are not. Contract-tested.

**2. Why can a TTL change not keep the existing entries?**

`TtlCache.ttlMs` is `readonly`, and an entry stores an absolute `expiresAt` stamped when it was
written. There is no "re-stamp everything" that is correct: entries written under a 60 s policy
were admitted on the strength of that promise, and re-dating them to a 2 s policy would expire
things that should still be live (or the reverse). Replacing the cache is the only answer that
cannot be subtly wrong. Observed: `entries` 14 → 0 the instant `cacheTtlMs` changed.

**3. What does write-only `connection.apiKey` avoid?**

Two distinct problems. **A second leak surface**: a credential that can be read back is a
credential that a mis-scoped read, an over-eager log line, a screenshot or a browser cache can
disclose. And **the round-trip footgun**: a settings form that renders what it read and posts back
what it renders would, the moment an operator changed the generative model and hit Save, post an
empty or masked `apiKey` and wipe the service-account token — taking the deployment offline with no
route back, from an unrelated edit. Hence: accepted on write, never returned, empty string means
"leave it alone", and the audit `detail` records `true` rather than the value (**D-CA-35**).

**4. Where did 500 come from on reset?**

`rt.envDefaults`, snapshotted in `buildRuntime()` before any override was ever applied, precisely so
that reset is a real operation. Without it, the first `PUT` would have overwritten the only copy of
the environment's value and "Reset to environment defaults" could only have meant "restart the
process". The same reasoning gives `rt.envBranding` its existence.

**5. The three refusals**

```
{"maxQuestionChars": 5}  → 400  "Invalid body: /maxQuestionChars must be >= 40"
                                errors: [{path: "/maxQuestionChars", message: "must be >= 40"}]
{"nonsense": 1}          → 400  "Invalid body: /nonsense is not an allowed property"
{}                       → 400  "No recognised settings in the request body"
```

Three different layers, in order: the **OpenAPI schema's range** (`route()` validated the body
against `SettingsUpdateRequest` before the handler ran); the schema's `additionalProperties: false`
(a typo'd key is a `400`, never a silent no-op — which matters a great deal for a settings API);
and the **service itself**, after validation passed, because an empty patch is a no-op an operator
should be told about rather than a `200` they will misread as "saved".
